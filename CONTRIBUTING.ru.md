# Как внести вклад

[English](CONTRIBUTING.md) | Русский

Спасибо, что хотите помочь проекту. Здесь собраны правила, по которым принимаются изменения.
Участвуя в проекте, вы соглашаетесь соблюдать [кодекс поведения](CODE_OF_CONDUCT.ru.md).

## Прежде чем начать

- Нашли баг, ошибку в документации или не хватает опции — откройте [issue](#issue).
- Новую библиотеку или изменение, которое ломает API, сначала обсудите в issue: так не придётся
переделывать готовый pull request.
- Опечатки, правки документации и очевидные баги присылайте сразу pull request-ом.

## Issue

Название issue пишется в формате `тип(библиотека): название`:

```text
bug(http-client-retries): не учитывается заголовок Retry-After
feature(grpc-client): опция для keepalive
docs(explicit-wait): в примере не указан таймаут
```

Тип — одно из трёх:

- `bug` — библиотека работает не так, как описано;
- `feature` — новая опция или возможность;
- `docs` — ошибка или пробел в README и скиллах.

Библиотека пишется так же, как каталог в `packages/`. Если issue не относится к одной библиотеке —
новая библиотека, CI, весь репозиторий, — скобки не нужны: `feature: библиотека для Kafka`.

В названии issue постарайтесь отразить главную суть проблемы или нового функционала.

## Окружение

Нужны [`uv`](https://docs.astral.sh/uv/), GNU Make и [`checkmake`](https://github.com/checkmake/checkmake), для тестов gRPC и SSH-клиентов — Docker. Все команды запускаются из корня репозитория:

```shell
make sync              # зависимости всех библиотек строго по uv.lock
make check             # форматирование, линтеры, mypy и тесты всего набора
make test-http-client  # тесты одной библиотеки
make help              # все доступные цели
```

CI проверяет код на Python 3.13 и 3.14. Вторую версию локально можно проверить так:
`make sync test PYTHON_VERSION=3.14`.

## Требования к коду

- Проверки строгие: ruff со всеми правилами, mypy в строгом режиме, предупреждения считаются\
ошибками. Линтеры и статические анализаторы должны проходить без ошибок.
- `noqa`, `type: ignore` и ослабление настроек проверок допустимы только с объяснением в pull request.
- Новую зависимость обсудите в pull request. Устанавливайте ограничения версий: `httpx>=0.28.1,<0.29`.
- Новое поведение и исправленный баг покрываются тестами в `packages/<имя>/tests`.
- Docstring пишутся в формате reST: `:param:`, `:returns:`, `:raises:`.
- Изменился API — обновите README библиотеки и скилл в `.agents/skills/<имя>-usage`.
- Расширения для клиентов оформляются опциями `ClientOption`, а не наследниками клиента.
Как устроены опции, описано в [README](README.ru.md#идея).

## Коммиты

Сообщения коммитов пишутся по [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/),
в скобках — имя библиотеки:

```text
feat(http-client-retries): учитывать заголовок Retry-After
fix(grpc-client-auth): обновлять токен до истечения срока
docs(explicit-wait): пример ожидания с таймаутом
```

Изменения, которые ломают API, отмечаются `!` после типа и строкой `BREAKING CHANGE:` в теле коммита.
Правки вне библиотек пишутся без имени пакета: `ci: ...`, `build: ...`, `docs: ...`.

## Версии

Версии следуют [SemVer](https://semver.org/lang/ru/). Автор pull request сам поднимает версию
в `packages/<имя>/pyproject.toml`:

- patch — исправление без изменения API;
- minor — новая возможность, старый код продолжает работать;
- major — изменение, которое ломает API.

Версия состоит ровно из трёх чисел, например `1.4.2`: другие форматы релиз не примет.
Если поднялась major-версия, обновите верхнюю границу в библиотеках, которые от неё зависят.
Правки, которые не попадают в опубликованный пакет (CI, корневые файлы), версию не меняют.

## Pull request

- Pull request открывается в `master`.
- В описании объясните, что изменилось и зачем.
- Pull request вливается после зелёного CI и одобрения мейнтейнера.

## Новая библиотека

1. Создайте `packages/<имя>` по образцу соседней библиотеки. Пакет в PyPI называется
 `cloudru-qa-<имя>`, модуль — `<имя>` через подчёркивание.
2. Добавьте пакет в `[tool.uv.sources]` корневого `pyproject.toml` и выполните `make lock`.
3. Положите в каталог библиотеки `LICENSE` и `README.md`  как в соседних библиотеках.
4. Опишите API в скилле `.agents/skills/<имя>-usage` и подключите его символической ссылкой
 из `packages/<имя>/.agents/skills`.
5. Добавьте библиотеку в список в корневом [README](README.ru.md#библиотеки).

Перед первым релизом мейнтейнеры подключают пакет к PyPI.

## Релизы

Релизы выпускают мейнтейнеры: ставят на коммит в `master` тег `<имя>/v<версия>`, например
`http-client/v1.0.0`. CI сверяет тег с версией в `pyproject.toml`, ещё раз прогоняет проверки
и публикует пакет в PyPI.
