# Reporting http_client calls in Allure

`http_client_allure` exports two `ClientOption`s and nothing else that matters:

| Option | What lands in the report |
|---|---|
| `wrap_requests_in_steps(...)` | a step per request + the request payload |
| `wrap_requests_and_responses_in_steps(...)` | the same + the response payload |

They are ordinary [`http_client`](https://github.com/cloud-ru-tech/qa-libraries/tree/master/packages/http-client) options: pass one to the client constructor and every call made through that client shows up in the report. No `allure.step` or `allure.attach` in the test code.

## Hard rules

1. Pass **one** of the two options, never both — each appends its own decorator, so every request would produce two nested steps with duplicate attachments.
2. The same option serves `HttpClient` and `AsyncHttpClient`; it detects the client type itself. There are no `async_*` variants to look for.
3. Inside endpoint methods call `self.send(request)` / `client.stream(...)`, **not** `self.client.send(request)`. The direct call bypasses the decorator and the request never reaches the report.
4. Do not wrap the call in your own `allure.step` "to be safe" — you get a step inside a step.
5. Put the option **last** in the constructor's option list unless you deliberately want otherwise — see "Ordering against other decorators" below.

Before debugging report output that looks wrong, read `references/pitfalls.md`.

## Quick start

```python
from http_client import HttpClient
from http_client_allure import wrap_requests_and_responses_in_steps

with HttpClient("https://api.example.com", wrap_requests_and_responses_in_steps()) as client:
    client.get("/orders/42")
```

The report gets a step `[GET] /orders/42` holding three attachments: `Request details`, `Response headers: status = 200 [OK]` and `Response content`.

Alongside the other options:

```python
import logging

from http_client import options
from http_client_allure import wrap_requests_and_responses_in_steps
from httpx import BasicAuth

client = OrdersClient(
    "https://api.example.com",
    options.with_auth(BasicAuth("admin", "PazzW0rD")),
    options.with_timeout(30),
    options.with_logger(logging.getLogger("orders")),
    wrap_requests_and_responses_in_steps(serialize_request_to_curl=True),
)
```

The request attachment is built from the request as it goes out, so headers added by `with_auth`, `with_default_headers`, `with_autogenerated_request_id` and any request hook are already in it.

## Parameters

Both options accept the same set; `attach_response` and `attach_response_headers` exist only on `wrap_requests_and_responses_in_steps`.

| Parameter | Default | Effect |
|---|---|---|
| `show_host` | `False` | put `scheme://host` into the step title |
| `show_query_params` | `False` | append the (masked) query string to the step title |
| `attach_request` | `True` | attach the request payload |
| `attach_response` | `True` | attach the response body |
| `attach_response_headers` | `True` | attach the response headers |
| `serialize_request_to_curl` | `False` | attach the request as a `curl` command instead of JSON |
| `sanitize_keys` | `None` | extra glom paths to mask |
| `use_default_sanitize_keys` | `True` | keep `http_client`'s built-in secret list |
| `json_dumps_kwargs` | `None` | `json.dumps` kwargs for rendering JSON; defaults to `{"ensure_ascii": False}` |
| `max_attach_length` | `None` | cut attachments longer than this many characters |

`attach_request=False` with `wrap_requests_in_steps()` gives bare steps and no attachments at all — useful when the payloads are huge or the report only needs the call sequence.

## What the attachments look like

`Request details` (JSON) — `query_params` appears only when the URL has a query:

```json
{
  "method": "POST",
  "url": "https://api.example.com/orders",
  "query_params": {"tag": ["new", "sale"], "token": "****"},
  "headers": {"authorization": "****", "content-type": "application/json"},
  "body": {"sku": "TEA-42"}
}
```

`Response headers: status = 200 [OK]` (JSON) — the response headers, masked the same way as the request ones. Repeated headers are joined with a comma, exactly as httpx renders them:

```json
{
  "content-type": "application/json",
  "x-request-id": "7f3c1a…",
  "set-cookie": "****"
}
```

`Response content` — parsed JSON when the response declares JSON, plain text otherwise. A response with an empty body produces **no** content attachment, but its headers still land in the report. The status code lives in the headers attachment name only: turn `attach_response_headers` off and the report no longer shows it.

The two response attachments are independent. Headers without the body:

```python
wrap_requests_and_responses_in_steps(attach_response=False)
```

With `serialize_request_to_curl=True` the request attachment is named `Request curl` and holds a runnable command with secrets already masked.

## Masking secrets

`authorization`, `cookie`, `x-api-key`, `token`, `password` and the rest of `http_client`'s default list are masked out of the box — in headers, query parameters, bodies, the curl command and the step title.

Add project-specific paths (glom syntax, same as `with_logger`):

```python
wrap_requests_in_steps(sanitize_keys=["client.pin", "items.*.token"])
```

httpx lowercases header names, so write `"authorization"`, not `"Authorization"`.

`use_default_sanitize_keys=False` replaces the built-in list instead of extending it — everything, including `authorization`, then shows in clear text. Use it only when a test must prove what was actually sent.

## Async

Identical option, identical parameters:

```python
async with AsyncHttpClient("https://api.example.com", wrap_requests_and_responses_in_steps()) as client:
    await client.get("/orders/42")
```

Concurrent calls through `asyncio.gather` each get their own step with their own attachments. The one difference: an async step does not show the request duration. That is deliberate — see `references/pitfalls.md`.

## Streaming

`client.stream(method, url)`, `client.stream_request(request)` and `client.send(request, stream=True)` all land in the report.

The body is not pulled out of the stream. `Response content` holds `<streamed content>` unless the calling code reads the body itself — then the real body is attached. The headers attachment is unaffected: headers are known as soon as the response arrives, so they are always the real ones.

```python
with client.stream("GET", "/events") as response:
    response.read()  # attached in full
```

```python
with client.stream("GET", "/dump.bin") as response:
    for chunk in response.iter_bytes():  # attachment stays <streamed content>
        sink.write(chunk)
```

The same applies to a streamed upload: its body is never read, so the report shows the placeholder rather than gigabytes of payload.

## Long payloads

```python
wrap_requests_and_responses_in_steps(max_attach_length=20_000)
```

Anything longer is cut and gets a `... (обрезано, полная длина: N символов)` footer. A truncated JSON attachment is downgraded to plain text — cut JSON is no longer valid and Allure could not render it.

## Ordering against other decorators

Decorators compose in the order the options are listed, and the last one added ends up outermost. So with a retry decorator in the mix:

```python
# one step for the whole call, retries hidden inside it
client = OrdersClient(base_url, options.with_send_decorator(retry), wrap_requests_in_steps())

# one step per attempt — every retry visible in the report
client = OrdersClient(base_url, wrap_requests_in_steps(), options.with_send_decorator(retry))
```

## Failures in the report

A connection error or timeout still produces a step, marked failed, with the request attached — the request is worth seeing precisely when it did not go through.

Building an attachment can never break the call: if masking or serialization fails, the report gets a short `<Ошибка формирования вложения: ...>` text attachment and the response is returned as usual. A request that already reached the server must not look like a network failure just because the report could not be drawn.
