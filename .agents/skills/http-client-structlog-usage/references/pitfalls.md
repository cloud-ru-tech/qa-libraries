# Pitfalls

Non-obvious behaviour that costs time when you hit it unprepared.

## Composite fields are JSON strings, not nested values

`headers`, `query_params` and a JSON `body` reach structlog already serialized. In a console renderer
that reads fine; under `JSONRenderer` the field is a string with escaped quotes inside the outer JSON:

```json
{"event": "http request sent", "body": "{\"user\": \"admin\"}"}
```

This is deliberate — nested structures would collide with field names of the surrounding application
context and would explode the index of a log store. If a collector must see the body as an object, parse
that string in a structlog processor of your own, do not expect the library to hand over a `dict`.

Consequence for `json_indent`: it puts real newlines inside those strings. Useful when a human reads the
console, harmful for a line-based collector — leave it unset in production.

## `logger` is annotated as the stdlib bound logger

The parameter type is `structlog.stdlib.BoundLogger`, but the hooks only ever call `.log(level, event, **fields)`,
which the default `structlog.get_logger()` also provides. It works at runtime; only the type checker
complains. Either configure structlog with `wrapper_class=structlog.stdlib.BoundLogger`, or accept the
mypy error at the call site.

## structlog does its own level filtering

`log_level` is just the level handed to `.log()`. If structlog (or the stdlib logging behind it) is
configured above that level, the record is dropped and the option looks broken. Lowering `log_level` to
`DEBUG` requires lowering the structlog threshold as well.

## Two logging options log everything twice

`with_structlogger` and `options.with_logger` append to the same hook lists and neither is aware of the
other. Both installed means two records per request in two different formats. Pick one.

## Every attempt is a separate pair of records

A retry inside `httpx.Auth.auth_flow`, or any send decorator that calls through more than once, re-runs
the request hook — with a **new** `trace_id` each time:

```
http request sent      trace_id=ae8ad3f7…
http response received trace_id=ae8ad3f7…   401
http request sent      trace_id=f0f27880…
http response received trace_id=f0f27880…   200
```

Each request pairs with its own response, but there is no field tying the attempts together into one
logical call. Add your own correlation field (e.g. `options.with_autogenerated_request_id()`, whose
header is generated per attempt too, or a bound context variable) if you need that.

## The request hook mutates the request

`request.extensions["trace_id"]` is written by the hook. Comparing `extensions` before and after a send
in a test will show the difference; it is not a stray mutation.

## The async hook reads the response body

An httpx response hook fires **before** the client has read the body, and on the async client the stream
is only reachable through `await`. So `parse_response_async` awaits `aread()` for buffered responses
before building the record. The caller sees no difference — httpx would have read the same body a moment
later — and a streamed response is skipped and stays unread.

This is why the library requires `http-client` 2.1: the helpers that tell a streamed response from a
buffered one became public API in that version.

## The hook is chosen by `isinstance(client, AsyncHttpClient)`

The option picks the sync or async response hook from the client type at construction time. A custom
async client that does not inherit from `AsyncHttpClient` gets the sync hook and fails on the first
response with `RuntimeError: Attempted to call a sync iterator on an async stream`. Inherit from
`AsyncHttpClient`.

## Masking never touches the response the caller receives

Every masking pass builds a copy. `response.json()` and `response.content` still hold the real values —
`****` exists only in the log. Do not use the option as a way to strip secrets out of the payload.

## `sanitize_keys` and the default list are not the same mechanism

`sanitize_keys` are exact glom paths: `user.password` masks that one field and nothing else. The default
list matches **by name at any depth**, so `password` anywhere in the body is already masked without any
configuration. Adding a default name to `sanitize_keys` is redundant, and adding a glom path expecting
name semantics ("mask `card_number` everywhere") does not work — the path must spell out the location,
`items.*.card_number`.

A path that matches nothing is skipped silently, so a typo in a path shows up as an unmasked field, not
as an error.

## Only JSON bodies are masked

`text/plain` and `application/octet-stream` bodies land in the log as they are. A token inside a plain
text body will be logged in full.

## A broken masking path shows up in one field only

Each part of the record is built inside its own `try`, so a glom path that raises spoils exactly one
field — `headers` becomes `<Error parse: ValueError>` while `body` stays correct. Do not read a single
`<Error parse: …>` as "logging is dead"; and note the exception message is dropped on purpose, so
diagnosing it means reproducing the path against the payload by hand.

## An absent `body` field is not an empty body

The field is omitted when there is nothing to log at all. An unsupported content type gives
`<not logged, content-type: …>`, an unread stream gives `<streamed content>`. Three different states, so
a log query filtering on `body` will silently skip bodiless records.

## Only `with_structlogger` is public API

`__init__` exports that one name. `event_hooks`, `parser`, `sanitizer` and the constants inside them are
internal: they moved in 1.0.0 and can move again. Filter logs by the event strings if you must, but do
not import them.
